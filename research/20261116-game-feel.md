# ゲームの手触り（juice / game feel）を Web UI に移植する

ゲーム開発で蓄積された「手触り」の技法を、Web の UI（ボタン、カード、フォーム、ダッシュボード）に移植するための調査メモ。
各節は **技法 / 効果 / 実装の勘所 / 数値 / 出典** の順に書く。数値は必ず **【実測】**（誰かが測った値・仕様値）と **【経験則】**（制作現場の推奨値・二次資料の要約）に分ける。
この文書は規則ではない（`research/README.md` の規約どおり）。規則化するなら `observations/` を経由する。

前提として、Web には「ゲームエンジンのタイムスケール」が無い。メインスレッドを止める凍結はできず、**論理時計を遅らせる／アニメーションを止める**形に翻訳する必要がある。以下の実装メモはすべてこの制約を前提にしている。


## 1. 画面振動（screen shake）

**効果**: 衝撃の「質量」と方向を伝える。カメラ（画面全体）を揺らすと、揺れていない物体との相対で衝突の大きさが読める。Vlambeer の Jan Willem Nijman は「The Art of Screenshake」（INDIGO 2013）で、銃撃・着弾・爆発に振動を足すだけで「撃っている感」が変わることをデモで示した。

**実装の勘所（Web）**:
- 揺らす対象は `position: fixed` のアプリ全体ではなく、**揺らしてよいラッパー要素**（`<main>` など）に限定する。固定ヘッダーやトーストまで揺らすと読みづらく、`position: fixed` の再計算でカクつく。
- `transform: translate3d()` + `opacity` のみを動かす。`top/left` や `margin` はレイアウトを再計算させるので使わない。
- 毎フレーム乱数を振らない。**滑らかなノイズ**（Perlin/simplex、または複数サイン波の合成）に振幅を掛ける。乱数だと「ジッター」に見え、ノイズだと「振動」に見える。
- 揺れは**基準姿勢からの相対オフセット**として加算する。基準座標に累積加算すると、揺れ終了後に画面がズレたままになる。
- `prefers-reduced-motion: reduce` では振動を 0 にするか、振幅を 1/4 以下に落として 1 回だけ小さく動かす（§10）。

**数値**:
- 【経験則】トラウマ値方式: 内部状態 `trauma` を 0〜1 で持ち、ヒットごとに **+0.3〜0.6**、**毎秒約 1.0** で減衰。振幅は `trauma²`（二乗）に比例させる。二乗にするのは、弱い揺れをほぼ消し、強い揺れだけを残すため。
- 【経験則】揺れの周波数は **数 Hz〜10 Hz 程度**。それ以上は「振動」ではなく「ノイズ」に見え、酔いやすい。
- 【経験則】持続は **0.15〜0.4 秒**。0.5 秒を超える連続振動は、UI では「壊れている」と読まれやすい。
- 【実測】Unity アセット Feel のドキュメントには、UI パネルの例として Duration 0.5 s / Amplitude 20 / Frequency 0.03、カメラの例として Duration 0.3 s / Amplitude 2 / Frequency 40 というプリセットが載っている（単位はエンジン依存で、そのまま Web の px には使えない）。
- 【実測】Bevy の `bevy_trauma_shake` は既定で `amplitude: 200, trauma_power: 3, decay_per_second: 0.3, frequency: 4, octaves: 2`。`trauma_power` を 2〜3 にすると減衰のカーブが変わる。

**酔い対策**: 振動は「画面の大部分が動く」ため、前庭障害のある人には強い不快を与える。回転（roll）を加えると酔いが増すので、UI では**平行移動のみ**にする。振動中も文字が読めるよう、振動は短く、入力の応答とは別レイヤーに置く。

**出典**: https://www.youtube.com/watch?v=AJdEqssNZ-U ／ https://gamedev-cheatsheet.com/concepts/screen-shake ／ https://bevy.org/examples/camera/2d-screen-shake ／ https://github.com/johanhelsing/bevy_trauma_shake ／ https://feel-docs.moremountains.com/screen-shakes.html


## 2. ヒットストップ（hitstop / freeze frame）

**効果**: 攻撃が当たった瞬間に世界（または関係者だけ）を数十 ms 止めると、脳はそれを「抵抗＝質量」と解釈する。止めないと、どれだけ派手なエフェクトを足しても「空を切った」感触になる。止めている間にヒットフラッシュを見せることで、接触の認知時間も稼げる。

**実装の勘所（Web）**:
- メインスレッドは止められない。代わりに **論理時計（`timeScale`）を 0.02〜0.1 に落とす**。CSS アニメーションなら `animation-play-state: paused` を一瞬入れる、WAAPI なら `animation.currentTime` を固定する、rAF 駆動なら経過時間に係数を掛ける。
- **入力キューは止めない**。凍結中に押されたキーは凍結明けに処理する。入力まで止めると「重い」ではなく「反応しない」になる。
- 止めた後は **1〜2 フレームで 1.0 に戻す**。急に戻すとプツ切れに見えるので、`timeScale` を 0.1 → 0.3 → 1.0 のように 2 段で戻す方法がある（【経験則】）。
- 音は止めない。BGM や効果音まで遅くすると、ピッチが下がって別の表現になる（Godot の `AudioServer.time_scale` に相当する処理を入れない）。

**数値**:
- 【経験則】軽い攻撃 **35 ms**、中 **55 ms**、重い **70 ms**、クリティカル **90 ms**。**120 ms を超えるとラグ（処理落ち）と読まれる**。
- 【経験則】弾丸・矢は **20〜30 ms** か、無し。飛翔体を止めると不自然。
- 【実測】Godot 4 では `Engine.time_scale = 0.0` にすると物理がゼロ除算で壊れるため、**0.02 を下限**にする。Web でも同様に係数 0 は避け、`0.02` などの下限を置く。
- 【経験則】ヒットフラッシュは **2〜3 フレーム**（60fps で 33〜50 ms）。白飛ばしは長いと色が読めなくなる。

**出典**: https://sharik.fr/game-feel/blog/en/hit-stop-game-feel ／ https://codingquests.io/labs/hit-stop ／ https://sourcegaming.info/2015/11/11/thoughts-on-hitstop-sakurais-famitsu-column-vol-490-1/ （Sakurai: ダメージ量に応じてヒットストップを変える）


## 3. パーティクル・破片・残像

**効果**: 「何が起きたか」を一瞬で説明する。破片は素材（ガラス・木・紙）を、残像は速度を、土埃は着地の重さを伝える。UI では、削除・送信・エラーなどの状態変化に「物質感」を与える用途が現実的。

**実装の勘所（Web）**:
- DOM で 1 粒 1 要素はすぐ破綻する。**Canvas 2D か WebGL**、もしくは 10〜20 個までの DOM なら `transform` + `opacity` のみ。
- 粒は**プール**して再利用する。イベントごとに生成・破棄すると GC スパイクでカクつく。
- 破片の初速に**ばらつき**を入れ、寿命で `opacity` を落とす。重力を入れると「重い」、入れないと「軽い」。
- 残像（trail）は**使いすぎると動きの切れが死ぬ**。GameAnalytics の解説は、トレイルが現在のポーズと数フレーム前の位置を混ぜるため「アニメーションのインパクトを妨げる」と明示している。UI では原則使わない。

**数値**:
- 【経験則】UI の破片は **6〜12 粒**、寿命 **300〜600 ms**、初速 **100〜400 px/s**。画面全体に散らすより、発生源から 100 px 以内に収める。
- 【経験則】パーティクル総数は 60fps 維持のため **同時 100 個以下**を目安にする（低スペック端末では半分）。
- 【実測】とはいえ「粒数とフレームレートの関係」を測った公開データは見つからなかった。実測するなら `performance.now()` でフレーム時間を記録し、粒数を 10/50/100/200 と振って p95 を比べる（この測定は未実施）。

**出典**: https://www.gameanalytics.com/blog/squeezing-more-juice-out-of-your-game-design ／ https://www.gamedeveloper.com/design/video-indies-resist-the-urge-to-juice-it-or-lose-it-


## 4. イージングの選び方

**効果**: 動きの「重さ・速さ・性格」を決める。等速（linear）は機械的に見え、ease-out は「反応が速い」と読まれる。UI では**入場は ease-out、退場は ease-in、移動は ease-in-out** が基本。

**実装の勘所（Web）**:
- 曲線は CSS カスタムプロパティに集約する（`--ease-out-quint` など）。コンポーネントごとにバラバラの `cubic-bezier()` を書くと、画面全体の性格が揃わない。
- **オーバーシュート**（y が 1 を超える曲線）は「跳ねる」印象。成功・獲得・ポップには合うが、エラーや削除には合わない。
- バネ（spring）は `cubic-bezier()` では厳密に表せない。CSS の `linear()` に減衰振動をサンプリングして入れるか、WAAPI/JS で物理を回す。`linear()` は 2023 年以降のブラウザで使える（要確認: 対象ブラウザの対応表）。
- `transition` は**プロパティを絞る**。`all` は意図しないプロパティまで動かし、レイアウトを誘発する。

**数値**（CSS の定義値・【実測】）:
| 名前 | cubic-bezier |
|---|---|
| `ease` | `cubic-bezier(0.25, 0.1, 0.25, 1.0)` |
| `ease-out` | `cubic-bezier(0, 0, 0.58, 1.0)` |
| easeOutCubic | `cubic-bezier(0.33, 1, 0.68, 1)` |
| easeOutQuint | `cubic-bezier(0.22, 1, 0.36, 1)` |

- 【経験則】UI の入場は **150〜300 ms**、退場は **100〜200 ms**。400 ms を超えると「待たされる」と感じ始める。大型のモーダルやページ遷移だけ 300〜500 ms を許容。
- 【経験則】マイクロインタラクション（ボタンの押下）は **80〜150 ms**。押した瞬間の `scale(0.97)` は 100 ms 程度で戻す。
- 【経験則】オーバーシュート量は **3〜8%**（`scale(1.05)` 程度）。10% を超えると子供っぽく、20% を超えると壊れて見える。

**出典**: https://developer.mozilla.org/en-US/docs/Web/CSS/easing-function ／ https://www.smashingmagazine.com/2021/04/easing-functions-css-animations-transitions ／ https://medium.com/@tangweikun123/css-easing-explained-picking-the-right-cubic-bezier-for-enter-exit-and-move-animations-e735d3522a45


## 5. 数値のポップ（ダメージ数字・カウントアップ・桁上がり）

**効果**: 変化の「量」を強調する。数字が飛び出す・跳ねる・桁が繰り上がる動きは、結果を「イベント」に変える。ゲームのダメージ数字がその原型。

**実装の勘所（Web）**:
- 数字は**等幅数字**（`font-variant-numeric: tabular-nums`）にする。プロポーショナルだとカウントアップ中に幅が変わり、レイアウトが揺れる。
- 桁上がり（odometer）は、各桁を別要素にして `translateY` で回す。`odometer` 系ライブラリは桁ごとに DOM を組み、CSS transition でスライドさせる実装。
- カウントアップは rAF で値を補間し、`Intl.NumberFormat` で整形する。桁区切りを自前でやるとロケールで壊れる。
- 値の跳ねは「最終値で 1 回だけ」。連打で毎回跳ねると、数字が読めなくなる。

**数値**:
- 【経験則】ポップの上昇は **150〜250 ms**、減衰して戻るまで含めて **300〜400 ms**。
- 【経験則】上方向への移動は **8〜16 px**、`scale` は **1.0 → 1.15 → 1.0**。
- 【経験則】カウントアップの総時間は **400〜800 ms**。1000 ms を超えると、ユーザーは「読み終わったのに待つ」状態になる。
- 【実測】`countup.js` と `odometer` の違いは実装方式（JS 補間か CSS スライドか）で、優劣の測定値は公開されていない。

**出典**: https://developer.mozilla.org/en-US/docs/Web/CSS/font-variant-numeric ／ https://npm-compare.com/countup.js,odometer ／ https://kpistudio.app/chart-types/count-up-animation


## 6. コンボ・連鎖・達成演出（音・光・文字の順序）

**効果**: 単発の成功を「連続する快感」に変える。コンボ数・連鎖・ランク表示は、同じ操作の反復に意味の階段を与える。重要なのは**量ではなく順序**で、同時に全部出すと情報が潰れる。

**実装の勘所（Web）**:
- 1 回の成功に対して、**音 → 光（フラッシュ）→ 形（粒子）→ 数字 → 画面**の順に、**0〜120 ms の範囲でずらす**。同時発火は「うるさい」になりやすい。
- 音は最初のフレームで鳴らす（遅延が最も知覚されやすい）。Web Audio はデコード済みバッファを再生すると遅延が小さい。`<audio>` 要素は初回再生に遅れが出ることがある。
- コンボ数は**更新のたびに前の値を消さず、加算の動きを見せる**（`+1` が飛んで合流する）。リセットは明示的に、間を置いて行う。
- 連鎖中は画面振動のトラウマ値を**加算ではなく上限付きで積む**。無限に積むと最後に画面が壊れる。

**数値**:
- 【経験則】コンボの猶予（次の成功までつながる）は **0.8〜1.5 秒**。短すぎると理不尽、長すぎると緊張が消える。
- 【経験則】達成演出の合計は **0.8〜1.5 秒**。2 秒を超えるとテンポを殺す。
- 【経験則】音の同時発音は **3 層まで**（アタック音・体感音・装飾音）。4 層以上は音割れと疲労の原因。
- 【実測】「順序を変えると評価が変わる」という統制実験は見つからない。ゲーム開発各社の経験則として提示されているものが多い（未確認）。

**出典**: https://www.youtube.com/watch?v=Fy0aCDmgnxg （Juice It Or Lose It, GDC Europe 2012） ／ https://www.gamedeveloper.com/design/video-indies-resist-the-urge-to-juice-it-or-lose-it- ／ https://www.gameanalytics.com/blog/squeezing-more-juice-out-of-your-game-design


## 7. 期待と報酬の間隔（可変比率強化スケジュール）

**効果（というより力学）**: 報酬が「毎回」ではなく「平均して N 回に 1 回」、しかも**ランダムな間隔**で与えられると、反応率が高く、報酬が途絶えても行動が消えにくい。Ferster & Skinner 1957 の可変比率（VR）スケジュールがこれで、Skinner はギャンブルとの関係を明示している。Zack et al. 2014 は、ラットで報酬確率 50% 条件が他の確率条件より運動反応を大きくしたと報告した（n=8/群、φ=0.986, p=0.025、著者自身が効果量は modest と明記）。

**Web UI への移植**: 「たまに大当たりする」通知、ランダムなボーナス、ガチャ的な演出は、この構造をそのまま持つ。**演出として面白いことと、依存を設計することは別**である。

**注意（必須）**: この節は**依存を煽る目的で使わない**。VR スケジュールは賭博・ソーシャルフィードの持続性と結びつけて論じられてきた構造であり、意図的に不規則な報酬を設計することは、ユーザーの行動制御を狙う設計に近づく。採用するなら、(a) 報酬の存在を事前に明示する、(b) 外れに罰を課さない、(c) 連続外れに上限を設ける、(d) オフにできる、の 4 点を満たす。ドパガキの文脈では「刺激の連続」と「報酬」を混同しないこと（`research/20261116-psych-refs.md` §1 の結論と同じ）。

**数値**: 【実測】VR の「平均 N 回に 1 回」という設定値そのものに普遍的な推奨は無い。上の実験値は動物実験の条件であり、UI の数値に直接変換できない。

**出典**: https://pmc.ncbi.nlm.nih.gov/articles/PMC3920462/ ／ https://www.bfskinner.org/wp-content/uploads/2015/05/Schedules_of_Reinforcement_PDF.pdf ／ https://www.simplypsychology.org/schedules-of-reinforcement.html


## 8. 触覚（navigator.vibrate）

**効果**: 視覚・聴覚に次ぐ第三のフィードバック。スマートフォンでは「押した」「当たった」を痺れで直接伝えられる。ただし**対応は限定的**で、振動の強さや波形を細かく設計することはできない。

**実装の勘所**:
- `navigator.vibrate(pattern)`。`pattern` は「振動 ms, 停止 ms, ...」の交互配列。`0` や空配列で停止。
- **スティッキーなユーザーアクティベーションが必要**。ページ操作前の自動振動は無視される。
- 端末がサイレント／Do Not Disturb だと振動しないことがある。**振動が無くても成立する演出**にしておく。
- パターンが長すぎると実装依存で切り詰められる。

**対応状況**:
- 【実測】MDN は「Limited availability / Baseline ではない（一部の主要ブラウザで動かない）」と明記。Chrome 系 Android は対応、**Safari / iOS は未対応**が長く続いている。
- 【未確認】2023 年頃に iOS Safari で動いたという報告が mdn/browser-compat-data の issue #29166 にあるが、公式の compat データには反映されていない。**iOS で動く前提を置かない**。
- 【実測】デスクトップの多くは振動ハードを持たず、呼んでも無効果（例外は出ない）。

**数値**: 【経験則】成功時 **10〜20 ms**、失敗時 **40〜80 ms**、パターンは 2 拍まで。連打で毎回振動させるとバッテリーと不快感の両方でマイナス。

**出典**: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate ／ https://github.com/mdn/browser-compat-data/issues/29166


## 9. 失敗時の演出（罰の強さ、リトライの速さ）

**効果**: 失敗の演出は「罰」ではなく**情報**であるべき。何がダメだったかを最短で伝え、やり直しまでの時間を最小にする。Celeste は死後ほぼ即座に部屋の最初へ戻し、プレイヤーは「罰は軽い／ほぼ無い」と語る。一方で「罰が軽すぎて失敗が他人事になる」という批判もある。

**実装の勘所（Web）**:
- 失敗の表現は **赤＋横揺れ＋短い低音** の 3 点セットが定番。ただし赤だけに頼らず、**アイコンとテキスト**を併用する（色覚多様性）。
- フォームのエラーは、入力欄の直近に出す。画面全体を揺らすのは「システム障害」の印象になるので、バリデーションでは使わない。
- **リトライは 1 アクションで**。エラー画面から戻るのに 2 クリック必要なら、それは罰。
- 失敗アニメーションで入力を受け付けない時間を作らない。アニメーションは非同期に走らせ、その間も再入力を受け付ける。

**数値**:
- 【経験則】失敗の振動は **100〜200 ms**、振幅は成功時の 2〜3 倍まで。それ以上は「怒っている」印象。
- 【経験則】リトライまでの待ちは **0〜800 ms**。1 秒を超えるとテンポが切れる。
- 【経験則】失敗音は **150〜300 ms** の下降（ピッチを下げる）。上昇音は成功に取っておく。
- 【実測】Celeste のリスポーンはプレイヤー報告で「0.5 秒程度」。ただし公式の仕様値ではなく、コミュニティの体感値（未確認）。ScienceDirect の研究は、プレイヤーが「罰が軽い」と認識して挑戦を続けたと報告している（質的研究）。

**出典**: https://www.sciencedirect.com/science/article/pii/S1071581923002082 ／ https://www.gentlegamers.com/celeste ／ https://steamcommunity.com/app/504230/discussions/0/1743395020138143278


## 10. 横断的な制約（Web 固有）

1. **`prefers-reduced-motion` を必ず尊重する**。MDN は Baseline（2020 年 1 月以降、主要ブラウザで利用可能）と明記。前庭障害のある人にとって、画面全体の拡大・パン・振動は不快・危険の原因になる。WCAG 2.3.3「インタラクションによるアニメーション」は、動きを無効化する手段を求める（AAA）。
2. **振動・点滅の上限**。WCAG 2.3.1 は 1 秒に 3 回を超える閃光を禁止する。ヒットフラッシュの連打はこれに触れうる。
3. **`will-change` は使い捨て**。常時指定すると GPU メモリを食う。アニメーション開始時に付け、終了時に外す。
4. **音はユーザー操作後に**。Autoplay 制限のため、最初のクリックで AudioContext を resume する。

**出典**: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion ／ https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html ／ https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html


## 11. 実装の優先順位（経験則）

すべてを入れると過剰になる。UI では次の順で効く（【経験則】、効果の大きさは主観）。

1. **応答の速さ**（押した瞬間に何かが動く。100 ms 以内）
2. **イージング**（linear をやめるだけで印象が変わる）
3. **失敗時の情報設計**（罰より速度）
4. **数値の変化の見せ方**（カウントアップ・桁上がり）
5. **振動・ヒットストップ**（ゲーム的な文脈のみ。業務 UI では過剰になりやすい）
6. **パーティクル**（最後。無くても成立する）

ゲームの「juice」は、しばしば**意味の伴わない装飾**になりうる。Folmer Kelly は「Juice It Or Lose It」への反論で、過剰な演出が没入と文脈を壊すと指摘した。UI では特に、**演出が情報を隠さないこと**を優先する。


## 12. 未確認・限界

- ヒットストップの 35/55/70/90 ms は**二次資料の要約値**で、一次の測定ではない。原典（Sakurai の Famitsu 連載、各ゲームの実装）には当たっていない。
- 画面振動の「酔いの閾値」を測った研究は見つけられなかった。周波数・振幅と不快感の関係は未確認。
- パーティクル粒数とフレームレートの関係は、この環境で計測していない（`ops_bash` が利用不可のため）。
- `linear()` イージングのブラウザ対応範囲は MDN の記述に依存しており、対象ブラウザでの実機確認はしていない。
- `navigator.vibrate` の iOS 対応は情報が矛盾している（issue 報告 vs 公式 compat）。**動かない前提**で設計するのが安全。
- 「順序をずらすと評価が上がる」という統制実験は未発見。順序の推奨は制作現場の経験則。
- Celeste のリスポーン 0.5 秒はプレイヤーの体感報告で、公式値ではない。
